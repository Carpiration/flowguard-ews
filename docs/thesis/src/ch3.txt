# ГЛАВА 3. РЕАЛИЗАЦИЯ И ЭКСПЕРИМЕНТАЛЬНАЯ ПРОВЕРКА МОДЕЛИ

## 3.1. Программная реализация модели

Модель реализована в виде программного средства FlowGuard. Исходный код размещён в открытом репозитории [@flowguard]. Средство представляет собой статическое веб-приложение: оно состоит из файлов HTML, CSS и JavaScript и не имеет серверной части. Разбор файлов, вычисление признаков, работа детекторов и хранение отчётов выполняются в браузере пользователя.

Такое решение принято по трём причинам. Первая — конфиденциальность: запись трафика содержит адреса и имена узлов организации, и её передача на внешний сервер нежелательна. При обработке в браузере файл не покидает компьютер пользователя. Вторая — простота развёртывания: приложение не требует установки и публикуется на любом хостинге статических страниц; требование 8 из таблицы 1.6 выполняется полностью. Третья — воспроизводимость: ядро модели не зависит от браузера и запускается в среде Node.js, поэтому эксперименты из данной главы повторяются одной командой.

Приложение разделено на три слоя. Ядро содержит разбор источников, вычисление признаков, детекторы и оценку качества; оно не обращается к элементам страницы. Слой интерфейса отвечает за графики, отчёты, хранилище и экспорт. Фоновый поток (Web Worker) выполняет анализ, не блокируя интерфейс: пользователь видит ход обработки и может её отменить. Состав модулей ядра приведён в таблице 3.1.

!t Таблица 3.1.|Основные модули ядра FlowGuard
| Модуль | Назначение |
| parse-pcap, decode | Чтение PCAP и PCAPNG, разбор заголовков Ethernet, IPv4, IPv6, TCP, UDP, ICMP, DNS |
| parse-text | Разбор CSV, JSON, NDJSON и вывода tcpdump; сопоставление названий столбцов |
| ingest | Определение формата по содержимому файла, потоковое чтение |
| features | Временные окна, 13 признаков, статистика пар узлов |
| score | Детекторы EWMA-z и CUSUM, объединение сигналов, состояния |
| iforest | Isolation Forest с робастной нормировкой оценки |
| patterns, catalog | Поведенческие сигнатуры, объединение в инциденты, описания и рекомендации |
| analyze | Конвейер анализа и построение отчёта |
| evaluate, lab | Показатели качества, ROC-кривая, эксперимент с абляцией |
| simulate | Генератор трафика офисной сети с размеченными атаками |

Формат входного файла определяется по его содержимому, а не по расширению: по сигнатуре в начале файла распознаются PCAP и PCAPNG, по структуре первых строк — CSV, JSON и вывод tcpdump. Поддерживаемые источники перечислены в таблице 1.2. Для табличных форматов названия столбцов сопоставляются со списком известных вариантов, поэтому файлы Wireshark, Zeek, Suricata и наборов CICIDS2017, UNSW-NB15, IoT-23 читаются без ручной настройки. Если в файле есть столбец с меткой атаки, отчёт дополняется показателями качества. Файлы читаются частями, что позволяет обрабатывать записи размером до 2 ГБ.

Приложение содержит семь разделов: обзор, анализ файла, мониторинг, отчёты, оценка модели, методология и настройки. Раздел «Методология» выводит формулы и пороги непосредственно из кода модели, поэтому описание не расходится с реализацией.

Корректность ядра контролируется автоматическими тестами. Набор из 22 тестов проверяет разбор адресов, времени и флагов, запись и чтение PCAP, разбор каждого табличного формата, работу Isolation Forest и CUSUM, вычисление показателей качества, отсутствие инцидентов высокой важности на трафике без атак, срабатывание всех сигнатур и сквозной анализ пяти файлов-образцов. Образцы создаются отдельным генератором на языке Python, независимым от генератора на JavaScript; это перекрёстная проверка разборщиков. Тесты запускаются при каждом изменении кода средствами GitHub Actions, и приложение публикуется только после их успешного прохождения.

Производительность измерена на записях разной длительности. Синтетическая трасса сохранялась в формат PCAP, после чего выполнялись разбор файла и полный анализ. Измерения проведены в среде Node.js в одном потоке; результаты приведены в таблице 3.2.

Из таблицы 3.2 следует, что скорость обработки составляет около 300 тысяч пакетов в секунду и почти не зависит от размера записи. Основное время занимает разбор файла; работа детекторов занимает доли секунды, поскольку они оперируют не пакетами, а несколькими сотнями окон. Двухчасовая запись объёмом 61 МБ анализируется примерно за три секунды. В браузере время несколько больше из-за передачи данных между потоками, но остаётся в пределах, удобных для интерактивной работы.

## 3.2. Анализ записей трафика и режим мониторинга

### Отчёт по записи трафика

Результатом анализа файла является отчёт. Его верхняя часть для синтетической записи офисной сети с семью атаками показана на рисунке 3.3.

!f report-top.png|Рисунок 3.3 – Отчёт по записи трафика: пиковый риск и сводные показатели|15.5

Отчёт начинается с пиковой оценки риска на шкале 0–100 и сводки: число инцидентов по уровням важности, суммарное время в состоянии тревоги, среднее время между первым предупреждением и тревогой, объём и длительность записи, число узлов. В приведённом примере запись длительностью 20 минут содержит 213,3 тысячи пакетов; модель разделила её на 240 окон по 5 секунд, обнаружила 7 инцидентов и оценила пиковый риск в 99 баллов.

Центральный элемент отчёта — временная шкала (рисунок 3.4). На верхнем графике показана интенсивность трафика, на нижнем — оценка риска с порогом тревоги. Серые полосы обозначают периоды атак по разметке, точки — моменты обнаружения инцидентов. Под графиком выводятся вклады детекторов.

!f report-timeline.png|Рисунок 3.4 – Динамика трафика, оценки риска и вкладов детекторов|15.5

Рисунок 3.4 наглядно показывает различие между «громкими» и «тихими» атаками, о котором говорилось в разделе 1.1. Первые четыре атаки почти не меняют интенсивность трафика на верхнем графике, и по объёму они неразличимы. Оценка риска при этом поднимается выше порога в начале каждой из них. Заметный рост объёма дают только утечка данных и SYN-флуд в конце записи.

Для каждого инцидента отчёт содержит карточку с доказательствами (рисунок 3.5): описание, время начала активности и обнаружения, числовые показатели, идентификатор техники MITRE ATT&CK и рекомендации по реагированию. Так выполняется требование объяснимости: оператор видит не только оценку, но и её причину.

!f report-incident-card.png|Рисунок 3.5 – Карточка инцидента с доказательствами и рекомендациями|12

Отчёты сохраняются в хранилище браузера и доступны в разделе «Отчёты». Предусмотрен экспорт в PDF, автономный файл HTML и CSV, а также перенос отчётов между устройствами через JSON.

### Режим мониторинга

Раздел «Мониторинг» демонстрирует потоковую работу модели (рисунок 3.6). Окна длительностью 2 секунды обрабатываются по мере поступления теми же детекторами, что и при анализе файла. Пользователь может в любой момент внедрить одну из семи атак и наблюдать, как модель переходит из нормы в предупреждение и тревогу; события фиксируются в журнале.

!f monitor-top.png|Рисунок 3.6 – Режим мониторинга: реакция модели на внедрённое сканирование портов|15.5

У этого режима есть ограничение, которое необходимо указать прямо. Браузер не имеет доступа к сетевому интерфейсу компьютера, поэтому источником трафика в мониторинге служит генератор, а не реальная сеть. Режим предназначен для демонстрации и обучения. Реальный трафик анализируется из файлов, записанных средствами tcpdump, Wireshark, Zeek или Suricata.

## 3.3. Методика эксперимента и наборы данных

Экспериментальная проверка состоит из двух частей. В первой части модель оценивается на синтетическом трафике, где начало и конец каждой атаки известны с точностью до секунды. Во второй части модель проверяется на реальном трафике набора IoT-23.

### Синтетический набор

Генератор имитирует работу офисной сети: 20 рабочих станций, внутренние серверы и внешние узлы. Фоновый трафик включает веб-обращения, запросы DNS, обращения к внутреннему порталу и файловому серверу, синхронизацию времени; интенсивность меняется случайным образом. Внешние адреса взяты из диапазонов, зарезервированных для документации [@rfc5737], чтобы набор не содержал адресов реальных организаций. На фон накладываются семь сценариев атак по расписанию из таблицы 3.3.

!t Таблица 3.3.|Сценарии атак в синтетическом наборе
| № | Сценарий | Начало, с | Длительность, с | Ожидаемая сигнатура |
| 1 | Разведка сети (ping-сканирование) | 210 | 60 | Разведка сети |
| 2 | Медленное сканирование портов | 320 | 150 | Сканирование портов |
| 3 | Подбор пароля SSH | 540 | 120 | Подбор учётных данных |
| 4 | Маяк управляющего сервера | 600 | 400 | Маяк |
| 5 | DNS-туннелирование | 720 | 100 | DNS-туннель |
| 6 | Утечка данных наружу | 860 | 120 | Утечка данных |
| 7 | SYN-флуд | 1060 | 80 | SYN-флуд |

Первые 210 секунд записи атак не содержат и служат периодом обучения нормы. Сценарии из таблицы 3.3 охватывают все стадии атаки, показанные на рисунке 1.1, от разведки до воздействия.

Генератор детерминирован: при одном и том же начальном числе (seed) он создаёт одинаковую запись. Чтобы результат не зависел от одной удачной реализации, эксперимент повторяется пять раз с разными начальными числами, и показатели приводятся как среднее и стандартное отклонение. Параметры эксперимента сведены в таблицу 3.4.

!t Таблица 3.4.|Параметры основного эксперимента
| Параметр | Значение |
| Длительность записи | 20 минут |
| Число прогонов | 5 (начальные числа 42, 7961, 15880, 23799, 31718) |
| Размер окна | 5 с (240 окон) |
| Порог тревоги | 50 |
| Исключаемый интервал после атаки | 30 с |
| Сравниваемые варианты | Ансамбль, порог μ+3σ, каждый детектор отдельно, ансамбль без одного детектора |

Сравниваются десять вариантов. Полный ансамбль сопоставляется с базовым методом μ+3σ. Четыре варианта «только один детектор» показывают, на что способен каждый компонент самостоятельно. Четыре варианта «ансамбль без одного детектора» показывают, что теряется при отключении компонента. Все варианты оцениваются на одних и тех же записях, с одним порогом и одним правилом исключения окон.

Следует сразу указать ограничение этой части. Синтетический трафик построен по известным закономерностям атак, и те же закономерности заложены в сигнатуры. Поэтому показатели на синтетических данных оптимистичны и характеризуют верхнюю границу качества. Их основная ценность — в сравнении вариантов между собой и в точном измерении задержки.

Он содержит записи трафика устройств Интернета вещей, заражённых вредоносными программами, и записи незаражённых устройств. Потоки сформированы системой Zeek и размечены специалистами лаборатории. Ансамбль превосходит базовый метод по всем показателям таблицы 3.6. F1-мера выросла с 0,40 до 0,95, площадь под ROC-кривой — с 0,70 до 0,99. Базовый метод обнаружил в среднем две трети сценариев, ансамбль — все. Ложных эпизодов тревоги у ансамбля не зафиксировано, у порога μ+3σ их 1,8 в час. Разброс F1 между прогонами у ансамбля составляет 0,010, у базового метода — 0,125: качество порога сильно зависит от случайной реализации фона.

Полнота ансамбля равна 0,912, а не единице. Пропущенные окна приходятся в основном на начало атак: первое окно атаки содержит лишь её часть, и риск ещё не достигает порога. На обнаружение сценариев это не влияет.

ROC-кривые вариантов для первого прогона приведены на рисунке 3.8. Кривая ансамбля проходит вблизи левого верхнего угла; кривая порога μ+3σ близка к диагонали на значительном участке, то есть для «тихих» атак порог ранжирует окна почти случайно.

### Вклад детекторов

Детектор EWMA-z, реагирующий на отклонение в одном окне, обнаруживает только половину сценариев. Isolation Forest на синтетическом наборе самостоятельно слаб: F1 = 0,24.

| Без Isolation Forest | 0,954 | 0,988 | 10,0 | 100 % | 0 |

Таблица 3.7 позволяет сделать три вывода. Отключение сигнатур обходится дороже всего: F1 падает до 0,72, а задержка возрастает более чем втрое. Отключение CUSUM увеличивает задержку на треть и приводит к пропуску части сценариев, что подтверждает его роль как детектора раннего предупреждения. Отключение Isolation Forest на синтетическом наборе не меняет показателей: всё, что замечает лес, уже замечено другими детекторами. Последний вывод относится только к синтетическим данным; на реальном трафике, как показано ниже, картина обратная.

Состояние предупреждения во всех сценариях таблицы 3.8 наступает через 5 секунд, то есть в первом же окне после начала атаки: это наименьшая возможная задержка при выбранном размере окна. Тревога объявляется через 5–20 секунд. Базовый метод сопоставим с ансамблем только на «громких» атаках — подборе пароля и SYN-флуде, которые сразу увеличивают число пакетов. В сценарии подбора пароля порог сработал на одно окно раньше. На «тихих» атаках порог отстаёт на 40–80 секунд, а разведку сети пропускает.

По всем пяти прогонам (35 сценариев) ансамбль опережает базовый метод в среднем на 81,7 секунды при стандартном отклонении 82,8 секунды и выдаёт тревогу раньше в 86 % случаев. Большой разброс объясняется неоднородностью сценариев: выигрыш близок к нулю для «громких» атак и превышает минуту для «тихих». Именно для последних раннее выявление и имеет практический смысл.

Результаты таблицы 3.11 заметно скромнее синтетических, и их следует разобрать по группам.

Запись Malware-34-1 ближе всего к условиям, для которых модель разрабатывалась: заражение начинается не сразу, атака продолжительна и включает DDoS и сканирование. Здесь ансамбль ранжирует окна почти безошибочно (ROC-AUC = 0,98 против 0,52 у базового метода), а точность составляет 0,99 при одной ложной тревоге на 122 нормальных окна. Полнота равна 0,47: модель уверенно выделяет активные фазы атаки, но не отмечает окна, где заражённое устройство лишь изредка обращается к управляющему серверу.

В записях Malware-20-1, 21-1, 44-1 и 42-1 вредоносная активность занимает от одного до семи окон из нескольких сотен. Показатели ROC-AUC ансамбля здесь составляют 0,61–0,90 и во всех случаях выше, чем у базового метода. Точность низка: при трёх-четырёх окнах с атакой даже 15 ложных срабатываний за сутки дают точность около 0,1. Запись 42-1, в которой вредоносная активность состоит из шести потоков загрузки файла в одном окне, моделью не обнаружена.

Важное наблюдение касается Isolation Forest. На синтетическом наборе он не давал вклада, а на реальных записях оказался самым полезным детектором: его самостоятельный показатель ROC-AUC составляет 0,93–0,99 на пяти записях. Причина в том, что реальные вредоносные программы не совпадают с заложенными в сигнатуры шаблонами, и именно метод без учителя замечает необычные сочетания признаков. Сопоставление показано на рисунке 3.11. Вместе с тем ансамбль на записях 20-1, 21-1, 44-1 и 42-1 уступает одному лесу: детекторы EWMA-z и CUSUM на разреженном трафике дают случайные срабатывания и ухудшают ранжирование. Это указывает на направление доработки — веса детекторов следует сделать зависящими от плотности трафика.

!f fig-3-11.png|Рисунок 3.11 – ROC-AUC на записях IoT-23: ансамбль, порог μ+3σ и Isolation Forest|14.5

Запись Malware-8-1 модель не распознаёт: ROC-AUC = 0,33. В ней заражение активно с первой минуты, и 275 из 288 окон относятся к атаке. Период обучения целиком состоит из вредоносного трафика, поэтому адаптивная норма принимает его за обычное поведение. Показатели базового метода для этой записи не приводятся, так как при 13 нормальных окнах они не несут смысла. Это прямое следствие допущения о чистом периоде обучения из раздела 2.1 и принципиальное ограничение любого метода, строящего норму по самой записи.

На записях незаражённых устройств доля окон с ложной тревогой составляет от 10 до 30 %. Причин две. Первая — разреженность: при одном-двух потоках в окне любое событие выглядит статистически значимым отклонением. Вторая — характер устройств: умные устройства регулярно обращаются к облачным сервисам производителя, и такое поведение по форме совпадает с маяком управляющего сервера. В записи Honeypot-4-1 сигнатура маяка сработала дважды именно на таких обращениях. В рабочей сети подобные адреса вносятся в список исключений.

### Ограничения модели

Результаты двух частей эксперимента позволяют очертить границы применимости модели (таблица 3.12).

!t Таблица 3.12.|Границы применимости модели
| Условие | Поведение модели | Подтверждение |
| Сеть с устойчивым фоном, атака начинается после периода обучения | Высокое качество, раннее предупреждение | Таблицы 3.6–3.8, запись Malware-34-1 |
| «Тихие» атаки: сканирование, маяк, туннель | Опережение порога μ+3σ на 40–80 с | Таблица 3.8 |
| Заражение активно с начала записи | Атака принимается за норму | Запись Malware-8-1 |
| Разреженный трафик одного устройства | Ложные срабатывания в 10–30 % окон | Записи Honeypot |
| Единичные вредоносные потоки | Не обнаруживаются | Запись Malware-42-1 |
| Законные периодические обращения | Похожи на маяк, требуют списка исключений | Запись Honeypot-4-1 |
| Атаки, видимые только в содержимом | Не обнаруживаются | Допущение раздела 2.1 |

Ограничения из таблицы 3.12 определяют направления дальнейшей работы. Первое — сохранение нормы между сеансами, чтобы оценивать новую запись относительно заведомо чистого периода, а не её собственного начала. Второе — учёт плотности трафика: увеличение окна и снижение веса статистических детекторов при малом числе событий. Третье — калибровка порогов сигнатур и весов детекторов на размеченных реальных данных; в данной работе параметры на наборе IoT-23 намеренно не подбирались, чтобы проверка оставалась независимой. Четвёртое — приём потоков в реальном времени от сетевого оборудования вместо анализа файлов.

Итог третьей главы: модель реализована, её формулы воспроизводимо проверены. На синтетическом трафике ансамбль обнаруживает все сценарии со средней задержкой 10 секунд и опережает порог μ+3σ в среднем на 82 секунды. На реальном трафике преимущество перед порогом сохраняется, но абсолютные показатели ниже, а на разреженном трафике и при отсутствии чистого периода обучения модель работает неудовлетворительно.
